# Matt 工作流与 Markdown 规范

本页负责阶段流转、文档归属和完成条件。依据2026-10-23读取的本机 Matt skills：ask-matt（含 PHASE-BOUNDARIES）、writing-for-agents、domain-modeling、to-spec、to-tickets、implement 与 code-review。需要使用某项技能时先读其 SKILL.md；本页不复制技能全文。

## 按任务规模选择流程

| 情形 | 路径 | 完成条件 |
| --- | --- | --- |
| 需求或边界尚不明确 | grill-with-docs | 本阶段影响实施的决策已确认，术语已记录，尚未解决的点有明确去向 |
| 问题必须运行才能回答 | 有界 prototype，再回到需求 | 保存问题、可运行证据和结论；原型不冒充生产实现 |
| 跨多次会话的工作 | to-spec → to-tickets | 验收入口获确认，规格及已确认任务发布到 GitHub，依赖明确 |
| 范围清楚、一次会话可完成 | Issue → implement | 按 Issue 完成修改、适用检查与验收，提交并回写证据 |
| 每个实现任务结束 | Standards 与 Spec 两个角度检查 | 分别核对写作／工程约定和需求验收；说明检查方式与限制 |
| 流程暴露重复问题 | retro | 将有效改进写入对应环境约定或检查，避免重复事故 |

本项目串行处理已解除阻塞的任务。只有真实前置条件才成为依赖；任务票交付可单独验证的完整小结果。已有 to-tickets 任务无需重复 triage。

当前对话可以继续完成工作；需要委派时，subagent 从任务 Issue 获取范围、验收和依赖，主 Agent 汇总并核查。模型与思考强度按 AGENTS.md 显式指定，只传入该子任务需要的上下文。已有执行对话仍可承接明确任务，Issue 承担任务记录，不自行创建新的独立对话。

2026-10-25用户已更新协作要求，允许按任务调动 subagent；此前“不新增子代理”的约束被本次要求替代。任务依赖与单一教师主线保持不变，实际采用的审核方式如实记录。

阶段边界先判断能否继续当前会话。仅在更换环境／目录、交给同事或分出支线时使用 handoff；需要保留的上下文才做 compact，任务独立且上下文可丢弃时再清理。单独切换一个聊天不等于完成 Matt 流程阶段。

## 文档职责与写法

| 文件／载体 | 只在这里维护的内容 | 写作与验收要求 |
| --- | --- | --- |
| README | 项目简介、使用入口、安装与本地依赖 | 让新读者知道先读哪份文档；动态进度指向 STATUS |
| AGENTS | 稳定约束与按任务触发的阅读指针 | 指针写清何时读什么；运行细节放职责文档 |
| STATUS | 当前阶段、任务链接、下一步及阻塞 | 简短快照；实验计数与日志用链接取证 |
| PROJECT | 当前业务边界、结果契约、暂停支线恢复条件 | 区分用户要求和设计建议；不积累逐轮进度 |
| GLOSSARY | 项目特有的已解决词义 | 每词1—2句，采用 domain-modeling 格式；有真实歧义才列避免用词 |
| docs/adr/ | 难逆转、无上下文会意外、确有取舍的决定 | 三条件同时满足才按需创建；通常1—3句讲清决定及原因 |
| 审核规则／工作释义 | 判断标准／标签范围提案与来源 | 规则与完成条件集中；冻结释义版本可回溯，结果指向实验记录 |
| DATA_AUDIT | 输入版本、字段、分母、质量事实 | 每个数据结论有可复核来源，事实与语义推断分开 |
| RESEARCH_AND_DECISIONS | 官方依据、方法候选、选择与替代理由 | 引用附查阅日期；公开项目能力不当本项目效果 |
| TEACHER_PATH_AND_TOOLS | CLI 操作、输入输出、故障与限制 | 参数以程序／help为准；方法比较指向研究文档 |
| EXPERIMENTS | 实际运行登记、分母、结论和证据入口 | 已完成／未运行／失败分开；原始日志放本地运行目录 |
| GitHub 规格／任务 | 问题、用户结果、决定、验收、依赖和完成证据 | 采用对应技能模板；实现决定避免易过时文件路径和代码抄录 |
| docs/history/ | 历史需求、旧计划、待续方案 | 冻结并标明来源时点与替代入口；不充当当前指令 |
| 本地 outputs／logs | 原文、逐项意见、预测、哈希、失败诊断 | 分版本保存，已有材料只读；公开文档仅链接或脱敏汇总 |

## 修改文档

1. 先按上表找到权威位置。相同含义只维护一处，其他文件用短指针；规则、理由和例外放在一起。
2. 把所有分支都需要的内容放在正文步骤；只有某分支才需要的材料放在按需引用中。步骤写可检查的完成条件，优先用明确动作表达要求。
3. 区分用户要求、已核实事实、设计建议与待验证问题。数字注明范围与分母，外部事实注明官方链接和日期，未运行不写成结果。
4. 替代内容移入历史档案或保留在已有版本中；修正时留下原因与新入口。新需求／任务更新 Issue，只有当前阶段变化才更新 STATUS。
5. 交付前检查改动范围、Markdown 相对链接、旧入口、公开内容和受保护文件哈希。文档改动做文档检查；改分类行为时再运行对应行为测试。
