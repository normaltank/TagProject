# Matt 工作流与 Markdown 规范

本页是流程权威，负责阶段流转、角色、文档归属和完成条件；任务事实与证据保存在 [GitHub Issues](https://github.com/normaltank/TagProject/issues)，记录格式见 [issue-tracker](issue-tracker.md)。

2026-10-26核对本机 Matt skills：ask-matt（含 PHASE-BOUNDARIES）、writing-for-agents、to-spec、to-tickets、implement、implement-spec、code-review。使用某项技能前仍须读其 SKILL.md。Matt 提供需求→规格→任务、逐票 implement／整批 implement-spec、固定基准双轴审查等步骤；本项目在此基础上规定默认委派、单一教师主线、串行实施、关票门槛和有界 API。模型配置以 [AGENTS](../../AGENTS.md) 为唯一权威。

## 按任务规模选择流程

| 情形 | 路径 | 完成条件 |
| --- | --- | --- |
| 需求或边界尚不明确 | grill-with-docs | 影响实施的决策已确认，术语已记录，待解问题有明确去向 |
| 问题必须运行才能回答 | 有界 prototype，再回到需求 | 保存问题、可运行证据和结论，作为后续需求依据 |
| 跨多次会话或多票工作 | to-spec → to-tickets | 验收入口经用户确认；每票是可单独验证的完整小交付，粒度与真实阻塞边经用户确认后发布 |
| 一张边界明确的任务票 | Issue → implement | 执行子代理交付、主 Agent 核验、独立双轴审查及归档关票均完成 |
| 整份已拆票规格一次实施 | implement-spec | 完成下述任务图、集成、整体审查与逐票关票步骤 |
| 流程暴露重复问题 | retro | 将有效改进写入对应环境约定或检查 |

to-spec 汇总已有讨论，to-tickets 发布已确认拆分；已确认的规格、验收和任务不重复访谈、triage 或审批。发现真实缺口时只补该缺口。仅把真实前置条件列为依赖，发布任务不关闭父规格。

## 角色与派工边界

- 主 Agent：读取当前状态和任务，明确边界、依赖、验收与文件归属，派工并核验证据，组织审查，最后归档和关票。用户指定的教师语义裁定由主 Agent 承担，并按审核规则保存为相应模型意见；这一角色不改变其他执行任务的默认委派。
- 执行子代理：在独立上下文按票实施，完成适用检查，逐验收项交付证据与待审提交；保持 Issue 开启，把验收与关闭留给主 Agent。
- 审查子代理：两个新上下文分别负责 Standards 与 Spec，只读审查同一版本，各自报告发现和限制。实施者不兼任自己的独立审查者。

小任务同样由执行子代理承接；主 Agent 继续当前会话做指挥和验收。派工显式使用 `fork_turns="none"`，模型与思考强度按 AGENTS 显式传入；提供 Issue、权威文档、基准与必要材料指针，不复制整段对话。所有子代理（含审查、merger）均遵守此配置，不另建独立聊天。

本项目串行实施已解除阻塞的任务，同一文件在一个时点只有一个写入者；依赖先后不得被并发绕过。两路只读审查可以并行，串行主线不限制审查轴的独立性。

## 单票 implement：进入、交付与关闭

1. **待执行 → 执行中。** 主 Agent 读取 Issue 正文、标签和最新评论，核对范围／排除项、逐项验收入口、固定基准、依赖就绪证据、文件归属和资源授权。条件齐备后在 Issue 留认领与分工记录，再派执行子代理。单写入者可复用当前干净工作区；有隔离需要才建工作区。
2. **执行中 → 待审查。** 执行子代理按票修改并做适用检查；代码行为按既定验收入口验证，文档任务检查链接、范围、规则一致性及保护材料。交付须逐验收项给出证据、限制和未完成项，列出基准与待审 head。可以先提交为待审快照，以供 code-review 的 `git diff <base>...<head>` 使用；运行成功、自报完成或形成提交都只到待审查。
3. **主 Agent 核验并派双轴审查。** 逐项检查交付物与证据，缺项退回实施者补齐。固定可解析的 base／head SHA，核对三点 diff 非空、提交列表和工作区状态；两个独立审查者使用完全相同的 SHA、diff 命令及提交范围。Standards 查仓库约定，Spec 查 Issue 与来源规格；分别保留结论、发现、证据及检查限制。
4. **待审查 → 待归档。** 主 Agent 将发现交回实施者修正。head 变化后重做适用检查，向两路审查者说明差异，由各轴复核受影响范围、确认此前结论对未变部分仍有效；记录最终 head 及两轴对该版本的结论。出现新范围或基准变化时重新确定审查范围。仅当逐项验收、适用检查及两轴结论全部通过，才进入待归档。
5. **待归档 → 已关闭。** 主 Agent 核对最终提交与审查 head 一致，归档证据，按已有授权同步远端，回填逐项证据、两轴结论及可访问的提交链接，再关闭 Issue。若仅获准本地交付，明确记录本地提交和同步限制，按约定的交付条件处理；需要远端链接而未同步时保持待归档。父规格在其全部交付与整体条件满足后才关闭。

待执行、执行中、待审查、待归档是 Issue 评论中的执行阶段，继续使用[五个 triage 标签](triage-labels.md)，不新增阶段标签。关闭是验收后的结果；进程退出、子代理完成通知、待审提交均不能替代第3—5步。

## 完整 implement-spec：多票集成

只有实际执行本节全套步骤才称 implement-spec；多张票逐张走上一节，仍称逐票 implement。

1. 主 Agent 读取规格和全部任务，建立含真实阻塞边的任务图，确定当前可实施前沿和集成分支。每票沿用派工前的范围、验收、基准与文件归属检查。
2. 每个实施者使用自己的分支及 worktree，从集成分支起步，按票实施和检查，交付前合入最新集成分支。Matt 原生允许并发前沿；本项目每次只派一个已就绪实施任务。
3. 每票交付后由独立 merger 子代理合入集成分支并检查集成结果，记录集成提交、该票验收证据与可供下游使用的产物。主 Agent 据此确认实施依赖就绪，再派下一个任务。**依赖产物已就绪与 Issue 最终关闭分开记录**：上游可保持待整体审查，其已验证的集成产物可解除下游实施阻塞；不能只等待上游关票才推进而卡住整体审查。
4. 全部任务集成后，对同一固定 base／集成 head 做一次整体 Standards／Spec 独立双轴审查；发现集中交给一个执行子代理修复，复核及最终 head 记录沿用单票第4步。各票实施结束不冒称整体审查通过。
5. 主 Agent 将整体结论映射回各票验收项，按单票第5步回填并关闭各票及父规格，报告集成分支；清理实施者 worktree，保留可恢复交付。仅在用户要求或跟踪器规定时走 PR；本仓库不以 PR 作为请求入口。

## 中断、接管与范围变化

- **主 Agent 接管实施：** 工具失败、执行者失联或用户明确要求接管时，先停止原执行者的写入及运行并核实停止状态；记录原因、已交付／未完成边界、文件归属、已用请求及未知请求状态，明确新的执行责任后再继续。接管是有记录的角色变更；后续验收与独立双轴审查照常进行。
- **API 与未知状态：** 接管或重试前核对已授权批次、实际用量与剩余额度。请求是否发出未知时保留未知，先查运行证据；不能视为0再重试。旧授权不自动补回已用或未知额度。原件与冻结材料只读，新输出另存版本。
- **范围或授权变化：** 更新任务边界、验收及依赖，必要时拆新票；已有授权内继续推进，只有确实超出范围、预算或必须由人决定的缺口才向用户说明并补授权。保留旧证据与变更原因，重新判定受影响检查。
- **工具／审查受阻：** 记录失败、已有证据、当前阶段及恢复条件，可用等价工具继续。无法取得必要证据或任一路独立审查时保持未完成／开启，报告真实限制，恢复后补齐门槛；不以主 Agent 自检代替独立审查。

阶段边界按 ask-matt 判断上下文动作：主 Agent 能继续就继续；跨环境、目录、同事或阶段中分支用 handoff；保留必要上下文才 compact，独立且可丢弃时再 clear。执行与审查的独立子代理按上述项目分工派出，切换聊天本身不构成阶段完成。

## 文档职责与写法

| 文件／载体 | 只在这里维护的内容 | 写作与验收要求 |
| --- | --- | --- |
| README | 项目简介、使用入口、安装与本地依赖 | 让新读者知道先读哪份文档；动态进度指向 STATUS |
| AGENTS | 稳定约束与按任务触发的阅读指针 | 指针写清何时读什么；运行细节放职责文档 |
| STATUS | 当前阶段、任务链接、下一步及阻塞 | 简短快照；实验计数与日志用链接取证 |
| PROJECT | 当前业务边界、结果契约、暂停支线恢复条件 | 区分用户要求和设计建议；不积累逐轮进度 |
| GLOSSARY | 项目特有的已解决词义 | 每词1—2句，采用 domain-modeling 格式；有真实歧义才列避免用词 |
| docs/adr/ | 难逆转、无上下文会意外、确有取舍的决定 | 三条件同时满足才按需创建；通常1—3句讲清决定及原因 |
| 审核规则／工作释义 | 判断标准／标签范围提案与来源 | 规则与完成条件集中；冻结释义版本可回溯，结果指向实验记录 |
| DATA_AUDIT | 输入版本、字段、分母、质量事实 | 每个数据结论有可复核来源，事实与语义推断分开 |
| RESEARCH_AND_DECISIONS | 官方依据、方法候选、选择与替代理由 | 引用附查阅日期；公开项目能力不当本项目效果 |
| TEACHER_PATH_AND_TOOLS | CLI 操作、输入输出、故障与限制 | 参数以程序／help为准；方法比较指向研究文档 |
| EXPERIMENTS | 实际运行登记、分母、结论和证据入口 | 已完成／未运行／失败分开；原始日志放本地运行目录 |
| GitHub 规格／任务 | 问题、用户结果、决定、验收、依赖和完成证据 | 采用对应技能模板；实现决定避免易过时文件路径和代码抄录 |
| docs/history/ | 历史需求、旧计划、待续方案 | 冻结并标明来源时点与替代入口；不充当当前指令 |
| 本地 outputs／logs | 原文、逐项意见、预测、哈希、失败诊断 | 分版本保存，已有材料只读；公开文档仅链接或脱敏汇总 |

## 修改文档

1. 先按上表找到权威位置。相同含义只维护一处，其他文件用短指针；规则、理由和例外放在一起。
2. 把所有分支都需要的内容放在正文步骤；只有某分支才需要的材料放在按需引用中。步骤写可检查的完成条件，优先用明确动作表达要求。
3. 区分用户要求、已核实事实、设计建议与待验证问题。数字注明范围与分母，外部事实注明官方链接和日期，未运行不写成结果。
4. 替代内容移入历史档案或保留在已有版本中；修正时留下原因与新入口。新需求／任务更新 Issue，只有当前阶段变化才更新 STATUS。
5. 交付前检查改动范围、Markdown 相对链接、旧入口、公开内容和受保护文件哈希。文档改动做文档检查；改分类行为时再运行对应行为测试。
